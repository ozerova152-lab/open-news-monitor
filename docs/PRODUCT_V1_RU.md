# Open News Monitor v1 — продуктовая структура и план разработки

## 1. Что мы строим

Open News Monitor — не «лента всех новостей интернета» и не редактор, который сам публикует контент. Это понятный self-hosted агент, с помощью которого человек или команда создаёт **свой монитор источников**:

1. указывает сайты либо описывает тему;
2. получает предложения источников и/или добавляет свои;
3. подтверждает, какие источники подключать;
4. получает только новые подходящие публикации с датой и ссылкой на первоисточник;
5. выбирает, куда получать результат: Telegram, email, Google Sheets или Markdown-файл.

Главный принцип: решение о выборе источников и использовании новости остаётся у человека.

## 2. Пользовательский путь v1

```text
Создать монитор
  ├─ «У меня есть сайты» → вставить ссылки
  └─ «Мне нужны источники по теме» → описать тему
                                  ↓
                       проверить и показать источники
                                  ↓
                       пользователь подтверждает список
                                  ↓
                 задать правила отбора и способ доставки
                                  ↓
                  первый запуск без отправки старого архива
                                  ↓
                 регулярные новые дайджесты со ссылками
```

## 3. Что уже работает

| Блок | Состояние | Примечание |
| --- | --- | --- |
| RSS/Atom-сбор | Готов | Заголовок, дата, прямая ссылка, защита от повторов |
| HTML-сбор | Готов | Требует проверенных селекторов одной карточки публикации |
| Открытый JSON-сбор | Готов | Только публичные endpoint без ключей и авторизации |
| Фильтрация и дедупликация | Готова | Локальная SQLite-память по URL |
| Защита от старого архива | Готова | Первый запуск создаёт стартовую границу без рассылки |
| Telegram, email, Google Sheets | Базово готовы | Подключаются только после явного выбора пользователя |
| Мастер начальной настройки | Частично готов | Пока проверяет RSS/Atom и работает через консоль |
| Планировщик | Работает для личного контура | Нужен универсальный сценарий установки |

## 4. Что должно войти в релиз v1.0

### A. Создание личного мониторинга

- понятный мастер без ручного редактирования JSON;
- выбор: свои ссылки или тема;
- несколько каналов доставки;
- выбор расписания;
- конфиденциальные данные хранятся локально или в секретах выбранной платформы, никогда не в Git.

### B. Подключение собственных источников

Пользователь вставляет URL. Система последовательно проверяет:

1. RSS/Atom;
2. открытый JSON/API;
3. HTML-страницу с повторяющимися карточками публикаций.

Результат всегда один из трёх: «можно подключать», «нужна доработка», «подключение следует отложить». До подтверждения пользователя источник не становится частью монитора.

### C. Необязательный каталог рецептов

Это не список «сайтов автора». Это набор готовых, технически проверенных рецептов для тех, кто хочет стартовать быстрее. Пользователь может:

- выбрать рецепт;
- изменить его;
- не использовать каталог вообще и добавить только свои источники.

Рецепт содержит URL, способ сбора, подтверждённые поля, дату проверки и статус. Он не содержит токенов, chat ID и личных настроек.

### D. Подбор источников по теме

Это второй сценарий после базового подключения по URL:

1. пользователь описывает тему и страну/язык при необходимости;
2. агент предлагает **только список** потенциальных первоисточников;
3. пользователь выбирает кандидатов;
4. система проверяет их технически;
5. только подтверждённые источники попадают в монитор.

ИИ не должен автоматически добавлять сайты или выдавать догадки о содержании публикации как факт.

### E. Понятный результат и здоровье системы

Каждая карточка содержит: источник, дату публикации, заголовок, прямую ссылку, короткое описание при наличии и причину попадания.

Пользователь должен видеть: дату последнего запуска, количество новых публикаций, список ошибок источников и состояние доставки. «Нет новых новостей» и «источник недоступен» — разные результаты.

## 5. Порядок разработки

| Этап | Результат | Когда этап считается завершённым |
| --- | --- | --- |
| 0. Продуктовый контракт | Эта схема, границы v1 и критерии готовности | Нет спорных трактовок: что агент делает и чего не делает |
| 1. Модель профиля | Один формат личного мониторинга: источники, фильтры, каналы, расписание | Профиль создаётся мастером и не содержит секретов |
| 2. Универсальная проверка URL | Один сценарий проверки RSS → JSON → HTML | Пользователь получает понятный статус и не видит технических трассировок |
| 3. Подтверждение и стартовая граница | Выбранный источник добавляется безопасно | Старые материалы не уходят как новые |
| 4. Выдачи и расписание | Telegram/email/Sheets + локальный запуск | Дайджест приходит только при новых совпадениях; ошибки отделены от пустого результата |
| 5. Каталог рецептов | Независимый набор проверенных источников | Рецепт можно выбрать, но пользователь не обязан это делать |
| 6. Подбор по теме | Список кандидатов с ручным подтверждением | Ничего не подключается автоматически |
| 7. Установка для новичка | Windows-ориентированный быстрый запуск + документация | Новый пользователь создаёт монитор без правки кода |
| 8. Качество и релиз | Тесты, примеры, журнал изменений, v1.0 | Три разных сценария проходят end-to-end |

## 6. Три обязательных сценария проверки

1. **Личный специалист:** следит за ИИ, инструментами и релизами.
2. **НКО:** следит за грантами, конкурсами и новостями доноров.
3. **Команда бизнеса/редактор:** следит за отраслевыми первоисточниками и конкурентами.

Если для этих сценариев требуется ручная правка кода, v1.0 ещё не готова.

## 7. Что нужно от пользователя проекта

Технических секретов и настройки GitHub сейчас не нужно. Нужны продуктовые решения и обратная связь:

1. **Первый главный пользователь:** кто для первого релиза важнее — самостоятельный специалист, НКО или небольшая команда/редакция.
2. **Первый результат:** какой канал считаем основным в демонстрации — Telegram, email или Google Sheets. Все три останутся возможностями агента.
3. **Три живых примера:** по одному примеру задачи и 2–5 сайтов для каждого из трёх сценариев. Это не попадёт в публичный репозиторий без отдельного согласия.
4. **Критерий полезности:** сколько времени должен экономить дайджест и в каком виде его удобно читать.
5. **Проверка понятности:** после каждого этапа пользователь проходит сценарий без помощи разработчика и отмечает, где было непонятно.

## 8. Рабочие решения по умолчанию

Пока не выбрано другое:

- интерфейс и документация — сначала на русском;
- продукт — local-first: данные и токены остаются у пользователя;
- Telegram — основной демонстрационный канал, email и Google Sheets — равноправные альтернативы;
- расписание запуска не является частью GitHub-кода: оно настраивается в окружении пользователя;
- GitHub Actions — дополнительный будущий способ размещения, а не единственный способ работы;
- исходники подключаются только после технической проверки и явного подтверждения пользователя.

## 9. Критерий готовности v1.0

Новый пользователь за 15 минут может без редактирования кода:

1. создать монитор по своим ссылкам;
2. проверить и подтвердить источники;
3. выбрать Telegram, email или Google Sheets;
4. сделать безопасный первый запуск;
5. получить новый дайджест с первоисточниками;
6. понять, если источник не сработал.
